# Dental support region: two mesh contours

> The two-contour face cut below is diagnostic. The live branch uses its side labels to construct narrow contour strips and sampled exact-face contacts; see [the design](../docs/superpowers/specs/2026-10-25-dental-contour-contacts.md). This is not clinically validated. See [support-module boundaries](support-module-boundaries.md) for the generic-vs-dental split and planned Early-Layer Islands check.

## Which result depends on which

The current path is `orientation → outer and inner mesh-edge loops → broad face cut → side labels → narrow mesh-distance strips → sampled contact faces → support build`.

The loops, not the broad face cut, define where the strips begin. The face cut is still required: `diagnosticDentalSideBands` reads `allowedFaces` to label the two incident faces of every contour edge as `openingSide` or `otherSide`. It starts a separate shortest-path search from each side. `proposeDentalContactFootprint` selects the `otherSide` results, then forms `contactFaces` from their union. It does **not** expand the entire `allowedFaces` component or find a new boundary around it. The source-face samples must lie in `contactFaces`.

This order matters. An edge alone gives a curve but no side. The old broad area gives a side but grants far too many possible contacts. Together, they produce a bounded strip measured along connected mesh faces. The current parameters and rejection rules are below. The [plain-language explanation](plain-language.md) uses the same order without the graph details.

Code layout changed without changing this algorithm: `src/core/analysis/dentalContours.ts` now detects the mesh-edge contours, and `src/core/analysis/dentalRegion.ts` performs the old face cut. `src/core/analysis/dentalContourEvidence.ts` independently validates one closed contour and returns each edge's two incident source faces; it deliberately does not choose a contact side.

The projected central-opening test reports `present`, `absent`, or `ambiguous`: no enclosed holes at both 256 and 512 pixels is `absent`; a stable, identical lifted mesh-edge loop is `present`; small/multiple holes, failed loop lift, or resolution disagreement is `ambiguous`. Current support generation requires `present`; `absent` remains inconclusive pending a real no-hole aligner.

`diagnosticDentalSideBands` in `src/core/analysis/dentalContactBand.ts` traces both local surface sides of each validated contour. It builds exact triangle adjacency from indexed mesh edges and seeds the two incident faces of each contour edge. Each seed starts at its 3D face-centroid-to-edge-midpoint distance. Bounded multi-source Dijkstra then accumulates 3D centroid distances through neighbors on the same side. The current settings omit centroids closer than 0.2 mm to the ridge and stop at 1.2 mm. `allowedFaces` labels the sides as `openingSide` and `otherSide`; the broad face cut does not grant contact permission. A missing opposing face or side separation makes the result inconclusive. The band function alone does not choose an anatomical side. `proposeDentalContactFootprint` currently chooses `otherSide` as a geometric candidate, not as a clinical certification.

`sampleDiagnosticContourContacts` in `src/core/analysis/dentalContourContacts.ts` supplies both the review markers and current production candidates. First, `inspectContourIncidence` requires one simple closed, two-sided mesh-edge loop. The sampler orders its vertices from the lowest indexed vertex and lower indexed neighbor. It measures segment lengths in original 3D millimeters, then samples the loop at `spacing/2 + k*spacing`. The GLB's lime and pink diagnostic markers use 2 mm spacing. The live footprint calls the same function at 3 mm for the outer loop and 2 mm for the inner loop. For each sample, search from the two incident faces without crossing a contour edge. Accumulate 3D centroid-path distance up to twice `maxSearchDistance`. Select the nearest reachable source-face centroid in the chosen strip within 1.5 mm. Skip a sample if both sides reach the strip or if no face qualifies. Keep each source face once. The result includes the face index, centroid, cross-product normal, distance along the loop, and distance from the contour. A disconnected-tetrahedron test proves the local search cannot jump across empty space. Rotation tests show stable face IDs on the saved reference. These tests do not prove anatomical side choice, body clearance, or printability.

For rim-gap diagnostics, `proposeDentalContactFootprint` can also be called with `samplePhaseFraction: 0`: its exact side-band masks are unchanged, but contact samples fall at `0 + k*spacing` rather than the production half-spacing phase. `selectDentalGapAlternates` receives the *built and retained* arclengths, the exact contour perimeter, and the phase-zero source-face samples. For each circular gap longer than twice the intended spacing, it chooses one candidate closest to the gap midpoint, excluding endpoints and invalid positions; a later build/recheck may need another round. The standalone crossing probe reports five such provisional opening-rim faces on the raw reference at 34, 44, 52, 62, and 68 mm. This is deterministic source-face evidence, **not** an approved contact. The live Step 2 preview and final builder still use only the half-spacing samples. A future repair must recompute alternate identities in both stages, run secondary-landing and full support-body clearance, and reconcile retained IDs before showing a candidate as safe.

`proposeDentalContactFootprint` in `src/core/analysis/dentalContactFootprint.ts` composes the preceding parts. Given the exact two-contour region and settings `(setback, width, outerSpacing, innerSpacing, maxSearchDistance)`, it computes all four side strips, unions the two `otherSide` masks as `contactFaces`, and samples each contour using independent arclength spacing. Invalid side strips or a failed sampler make the result inconclusive. Current one-reference defaults are 0.2–1.2 mm strip bounds, 3 mm outer spacing, 2 mm inner spacing, and 1.5 mm maximum local search, grouped in `defaultDentalContactFootprintSettings`. The narrower inner spacing was chosen after the earlier 5 mm sampling left a 25 mm unsupported final opening-rim arc on the reference; it is not a validated universal spacing. Every contact carries an exact source face ID inside `contactFaces`, outside the broad opening-facing region. The ideal example has 89/90 simple-column tops within 0.4 mm of these strips, but does not prove safe approach/body paths. `proposeDentalSupportRegion` now includes the footprint; the placement worker recomputes it from the STL, compares the saved contour and contact mask byte-for-byte, then transforms these sampled contacts into the print frame. Painting can remove or restore only candidate faces. Old saved policies without `contactFaces`/`contacts` fail closed. The viewport and GLB exporter show `contactFaces` as teal; call it the **aligner contact strip**, with the mesh-edge curves as its trim rims. For a no-central-opening aligner, a separate validated outer-only variant is needed; do not synthesize a missing inner loop.

Operator tuning is a typed `DentalTuning` value in `src/core/analysis/dentalTuning.ts`: `(setbackMm, stripWidthMm, density)`, default `(0.2, 1.0, 1.0)`. The conversion to footprint settings is `setback = setbackMm`, `width = setbackMm + stripWidthMm`, `outerSpacing = 3 / density`, `innerSpacing = 2 / density`, and `maxSearchDistance = 1.5` (millimetres except dimensionless density). UI bounds are `0 ≤ setbackMm ≤ 1`, `0.2 ≤ stripWidthMm ≤ 2.4`, and `0.5 ≤ density ≤ 2`; these are interface limits, **not clinical safety ranges**. Invalid or nonfinite values are refused. Step 2's 180 ms-debounced analysis-worker retune reuses the accepted exact contours and broad side labels, recomputes the narrow face mask and exact source-face samples, and replaces the unit policy atomically. The brush stamps remain in that policy and apply only inside the new mask. Changing controls immediately invalidates the old tip preview; the new overlay and proposed tips appear after worker recomputation, with Next disabled while it runs. The final builder independently reruns full contour detection using the saved tuning and compares loops and masks, refusing stale or forged primaries. Its final rim-gap warning uses the tuned outer/inner spacings. Old projects without tuning reproduce the original defaults. Browser verification on the centred reference changed 13,176 to 13,815 allowed faces by widening the band, then 117 to 130 proposed tips by raising density, then 13,815 to 10,856 faces by moving setback; these are one-model UI/parity observations, not anatomical certification.

Each exact trim rim has a **cavity-facing width** and a **non-cavity-facing width**, measured by shortest connected surface path from the curve, not by screen-space offset. The current `(setback, width)` bounds describe only the non-cavity-facing permitted band; the cavity-facing band is diagnostic and has zero automatic contact permission. This distinction stays the same for outer and central-opening rims, whereas geometric “inside/outside” reverses. A future additional-support or island-repair pass may place a contact only on a permitted face in this strip; its width cannot itself certify a safe shaft, tip, or print result.

This document describes `proposeDentalSupportRegion` in `src/core/analysis/dentalRegion.ts`. It is a reproducible detector measured on one owner-approved [`reference-aligner.stl`](../docs/dental-reference/reference-aligner.stl); thresholds are not validated on other patients. Step 1 Next accepts a successful proposal; Step 2 shows its narrow contact mask and tips; Step 3 builds supports. A failed or changed mask yields no automatic tips. See [the plain-language explanation](plain-language.md).

## Technical reconstruction

### Input and output contract

Call `proposeDentalSupportRegion(mesh: TriangleMesh)`. The input has indexed vertex positions and triangles in local coordinates. `proposeDentalOrientation` first supplies the opening direction and a perpendicular tangent/bitangent frame. The result is a discriminated union:

- `kind: 'proposal'`: `allowedFaces[i]` is the **broad diagnostic** underside face cut; `contactFaces[i]` is the narrow production candidate strip; `contacts` are ordered exact source-face samples. `outerEdges` and `openingEdges` are flat pairs of vertex indices (unordered edge set). `outerRidgeEdges` holds the two original 60° chains; `outerConnectorEdges` holds the two 20° graph joins. Diagnostics give broad region face counts and connector lengths in STL units.
- `kind: 'inconclusive'`: a machine-readable reason. No partial mask or contour is returned.

The returned mask is tied to the **input triangle indices**, not a transformed world-space raster. Rotating the mesh should leave the per-face answer unchanged. No 2D brush or vertex-color approximation is used to decide membership.

### Orientation frame used by detection

Calculate the mean vertex position and the unnormalized 3 × 3 covariance matrix of all vertex offsets. Its smallest-eigenvalue eigenvector is the candidate cavity axis. Reject the mesh when the smallest eigenvalue divided by the largest exceeds `0.6`. Project vertices onto the axis. Measure triangle area in the outermost 14% of the projection range at each end, using triangle centroids. The end with *less* area is the opening. Reject an end-area difference below 18% of their sum. Reject confidence below `0.12`, where confidence is the end-area difference ratio times one minus the eigenvalue ratio.

Let `openingDirection` point toward the lower-area end. Choose reference axis `(1,0,0)` unless `abs(openingDirection.x) >= 0.8`, then use `(0,0,1)`. Set `tangent = normalize(reference × openingDirection)` and `bitangent = normalize(openingDirection × tangent)`. Project a vertex `p` to `(dot(p-centroid,tangent), dot(p-centroid,bitangent))`. The rim-centroid translation does not change edge connectivity or planar extents. The production orientation helper also builds a provisional rim and visibility mask; the two-contour face cut does not use those masks.

### 1. Construct the mesh graph

For each triangle, calculate its unit normal and its three undirected edges. Welded/indexed edges must each have exactly two incident faces; reject a boundary, non-manifold edge, or degenerate triangle. Store vertex coordinates projected into the opening-plane frame for later extent and hole tests. Edge length and face adjacency always come from the original 3D mesh.

For neighboring face normals `n1,n2`, an edge passes a sharpness threshold `θ` when `abs(dot(n1,n2)) <= cos(θ)`. The absolute value follows the exploratory probe; it tolerates locally reversed winding but does **not** repair globally inconsistent normals. Thus 60° finds strong ridge sections, while 20° allows a weaker connecting ridge.

### 2. Close the outer ridge

At 60°, sort connected edge components by edge count. Require the largest two to be simple open chains: exactly two degree-1 ends, every other vertex degree 2, `edgeCount = vertexCount - 1`. On this sample they have 1,628 and 831 edges. Require at least 500 and 300 edges respectively; the largest must span at least 60% of the full model extent in *both* opening-plane axes. These are conservative sample-derived rejection checks, not anatomical laws.

Make a 20° sharp-edge graph, excluding edges already in the two chains. For both possible end pairings, find shortest paths by accumulated **3D Euclidean edge length** with Dijkstra. Combine the two chains and two paths. Accept the shorter total pairing only if every vertex has degree 2 and the number of edges equals the number of vertices: one simple closed contour, with no branch or crossing. Here the connectors are 10.55 mm/38 edges and 40.39 mm/168 edges; the full loop has 2,665 edges. The two original chains contain 2,459 edges and export in blue. The 206 added path edges export in green, even if an individual connector edge also passes the 60° test. Color records *how the detector selected it*, not its angle alone. This is a surface-following path, not a straight join, but its long connector still needs anatomical review.

### 3. Recover the inner opening loop

Project every triangle to the tangent/bitangent plane and rasterize its occupancy with pixel-center triangle tests, leaving a two-pixel margin. Flood-fill empty pixels in four-neighbor connectivity. The one empty component not touching the image border is the central opening; require exactly one hole occupying at least 1% of the image.

For each mesh edge, keep it if its incident face normals have opposite signs against the opening direction **and** its projected midpoint is within two pixels of the hole. This lifts a projected silhouette back onto actual mesh edges. Build an edge graph. On the reference it contains one 339-edge closed loop and one three-edge false loop sharing a degree-4 vertex. Keep the large loop only if there is no other branch and any extra loop has at most 10 edges. Run independently at 256 and 512 pixels and demand the **same exact mesh-edge set**; otherwise abstain. The red central-opening contour is 339 edges on this sample.

The raster only helps locate a hole. It never defines the final 3D support region, and disagreement between resolutions is a rejection signal.

### 4. Cut and classify mesh faces

Construct the triangle-adjacency graph. Block adjacency across every outer-loop and inner-loop edge. Require exactly two connected face regions. Calculate each region's mean face-normal dot against the detected opening direction. Choose the more opening-facing region only when its mean is at least `+0.2`, the other is at most `-0.15`, and the chosen region has 20–85% of all faces. Set `allowedFaces` by flood-fill region membership; no projection band, local height plane, or “all downward normals” rule is applied.

On the reference the cut yields 254,344 opening-facing faces (mean dot `+0.381`) and 119,612 other faces (mean dot `-0.299`). Either contour alone does **not** isolate these groups. Both closed loops are necessary. The 254,344-face group is a side label, not the live support area. `proposeDentalContactFootprint` selects 13,176 faces in the narrow `otherSide` strips on this reference.

### Retained methods that no longer grant contacts

The project retains the older work for comparison and possible reuse:

- The first `lower-edge-loop` and opening-ray visibility method identified a tiny ridge on the reference, not the full trim. It also missed underside surfaces and allowed some exterior contacts. `src/core/analysis/dental.ts` still contains the legacy orientation and rim helpers. See the [reference failure images](../docs/dental-reference/README.md) and the historical checkpoints in [`docs/dental-rework-handoff.md`](../docs/dental-rework-handoff.md).
- A later probe found the largest smooth opening-facing patch. In side views that patch extended nearly the full axial depth and reached tooth-height surfaces. The probe remains in `scripts/probe-dental-edges.ts`; it is not a contact permission rule.
- The two-contour face cut above fixed the boundary shape and covered surfaces missed by rays. We first used its full `allowedFaces` mask for support placement. That produced 397 proposed tips on one reference run and visibly overpainted areas above the intended trim. The live path now keeps `allowedFaces` only for side labeling and contour checks. The older broad-mask GLB remains in [`docs/dental-reference`](../docs/dental-reference/README.md).

Keep these methods and measurements distinct when testing a future STL. A new use of a retained method needs its own face labels, support-path checks, and tests. Do not treat an old teal review image as the live narrow mask.

### 5. Sample narrow contacts and check secondary landings

The Step 2 placement worker no longer samples all downward-facing broad-region triangles for two-contour aligners. It recomputes the exact footprint, compares both contour edge sets and broad/narrow masks to the saved policy, filters its ordered contacts through the current paint stamps, and transforms retained exact source-face centroids/normals into the print frame. Step 2 records proposed tip IDs but does not build full supports. Step 3 independently repeats the footprint comparison and accepts each saved automatic primary point only if it matches a current exact source-face sample within 0.03 mm, with normal dot above 0.95, and remains paint-allowed. Invalid automatic points are reported as dropped; manual supports are kept. Then `LineTarget.cast` first casts against the exact indexed source mesh for secondary landings. Its hit carries a face index and hit point; voxel-remeshed visible geometry must retain that original identity.

For each automatic column that lands on the model, and each automatic tree junction that lands on the model, transform the exact hit point back to unit-local coordinates. Calculate the source triangle's geometric normal from its three indexed vertices. Call `dentalRegionAllowedOnFace(policy, faceIndex, localHitPoint, normal)`. If it returns false, omit that column or all members of that tree. A support that lands on the build plate has no second model contact and needs no second-face test. The rule does not reject manual supports. Record the omitted contact IDs in `dropped`; keep painted-zone omissions separately in `droppedByZones`.

The secondary-landing gate checks contact points, not intersections along the generated body. A separate automatic-pillar pass now builds the actual support mesh, tests shaft triangles against indexed source-model triangles (including coplanar overlaps), omits the crossing automatic contact IDs, rebuilds, and rechecks. If the rebuilt automatic layout still crosses, it fails closed to manual-only supports. Intentional primary-neck and approved secondary-tip reach are excluded from this narrow pillar classification. The pre-fix reference had 107 pillar intersection pairs from two automatic contacts; the filtered one-reference output has zero forbidden automatic-pillar intersections in the independent BVH diagnostic. A fresh whole-mesh BVH audit found 3,502 neck/model triangle pairs across all 83 retained contacts, with 1,981 pairs on faces outside the narrow band. Those intersections need a separate depth/direction classification; a face-strip check cannot certify them as intentional. No other component intersections appeared on this one fixture, but that does not guarantee clearance for braces, trees, roofs, manual supports, or other patient meshes. Early-layer island detection is not implemented.

`bodyIntersection.ts` now owns the reusable `intersectingSupportComponents(model, builtMesh, select, skipLandingTips)` search. It builds a model-triangle spatial grid in X/Z for each call, searches only cells overlapping a selected support triangle, rejects disjoint 3D axis-aligned boxes, then calls the generic exact `trianglesIntersect3D` kernel. `dentalBodyClearance.ts` owns only dental component/ID selection. This is much cheaper than testing every support triangle against every model triangle, but the grid is not yet cached across preview/export/rebuild. Both meshes must be in the same millimetre frame. Planned generation-time preflight reuses one model index to reject obvious pillar routes and brace/tree segments before meshing, trying only a bounded set of alternate automatic contacts in the permitted region. Definitive exact checking still runs after actual mesh construction and before display/export because a clear centre line does not prove tapered tips, junctions, or full diameters clear.

Dental structure settings are per-policy booleans `structure.treeEnabled` and `structure.bracesEnabled`, both `true` when absent (including older projects). `dentalBuildSettings` maps them to generic `scatterAutoTree` and `trussEnabled` and always forces `roofMode: OFF` and empty roof seeds. After the first actual build, `crossingSupportStructureParts` uses the same exact model-triangle grid and triangle intersection kernel on `tree-branch`, `tree-trunk`, and `brace` components. A non-exempt crossing tree forces a rebuild with Auto Tree off; a crossing brace forces a rebuild with bracing off. The final result records `dentalStructureFallback`, shown as a Step 3 warning. A last structural check after pillar rejection prevents a changed layout from escaping this gate; unresolved structural intersection falls back to manual-only geometry with trees and braces off. This is deliberately conservative and may reduce rim coverage. It does **not** certify every neck penetration, manual shaft clearance, island stability, or another patient's STL. The saved raw reference still requests trees but rejects them for body crossings in the focused rim-coverage regression.

Collision evolution and reuse boundary: the original automatic-pillar check was necessary but insufficient. Enabling Auto Tree on the raw reference changed 117 proposed / 15 omitted to 117 / 21, raised the largest opening gap from 8 to 10 mm, and the independent BVH probe measured 402 `tree-trunk` plus 670 `tree-branch` triangle-intersection pairs (352 and 516 respectively against faces outside the contact band), despite zero pillar crossings. This falsified the assumption that bounding the contact strip, choosing a safe landing, or leaving a nominal shaft margin automatically clears spanning structures. The production code therefore checks exact triangles *after* the actual builder and reruns with the unsafe structure off, then performs the pillar-id rejection and one last structural check. `trianglesIntersect3D` and the X/Z-indexed `intersectingSupportComponents` search are generic; `crossingSupportStructureParts` and `crossingAutomaticBodyContactIds` in `dentalBodyClearance.ts` choose dental components. The generic search is standalone and tested, and dental now reuses one index across its checks, but generic jobs do not yet enforce body clearance. A future generic policy caller must distinguish intentional reach and report part/contact attribution, leaving each product mode to choose its own fail-closed action. Do not generalize the dental whole-mode fallback as the universal behavior for generic supports.

Historical false-positive boundary: for the default round/tapered tip, `treeGeometry` can emit the contact-adjacent neck and the rest of the branch under one `tree-branch` component. The earlier structural checker treated every intersection of that component as forbidden and could turn off an otherwise valid Tree solely because its intended tip penetrated the shell. The reference also has `tree-trunk` intersections outside the contact strip, so its Tree fallback is independently warranted; this does not validate every branch-tip classification. This motivated explicit tip provenance and a bounded intentional-contact test. Brace and trunk checks have no intended primary contact exception.

Provenance and current narrow classifier: each `treeGeometry` branch records primary contact point(s)/normals and, if it lands on the model, its secondary hit point/normal/source face. A joined two-leaf branch records **both** primary IDs; shaped-tip neck segments carry the nearest endpoint intent. `supports/supportFrame.ts` transforms intent points and normals with the support vertices. `dentalPrimarySourceFace` matches each accepted automatic dental contact back to one exact contour sample face; ambiguous matches leave the face absent and cannot receive an exemption. `supportBodyConflicts` reports the first non-exempt model-face/support-triangle hit per component, but continues past a locally approved hit to find another wall. `isIntentionalContactReach` accepts a hit on the exact tagged source face **or one face sharing exactly one indexed edge** with it; both hit and source face normals must agree with the intended contact direction. All support-triangle vertices must lie within `neckLength + pillarDiameter/2 + contactRadius` of the intended point, and penetration along the outward normal must be no deeper than `max(0, tipDepth) + contactRadius + 0.05 mm`. Invalid geometry/limits, unknown source faces, nearby topologically separate walls, reversed source-face winding, and long branch spans remain conflicts. This is an O(1) one-edge check per hit; it does not flood a whole connected mesh side. Dental Tree policy uses this narrow predicate; Trunk and Brace receive no exemption. It remains conservative beyond one adjacent face, and generic contacts do not yet carry a certified face. The reference's Tree fallback remains. These formulas are engineering bounds for classifying an intended local reach, not dental or print acceptance thresholds.

Current independent reference check after this classifier: the raw saved aligner proposes 117 automatic tips and omits 15; the built output has 38,344 support faces, zero forbidden automatic pillar crossings by both the core ID check and independent BVH report, and an 8 mm retained opening-rim gap. The independent BVH still finds **4,323 neck/model triangle pairs**, **2,478 outside the narrow contact band**. These are measured triangle intersections, not 4,323 distinct bad supports, but their intent/depth is unresolved. The new Tree exception does not certify or suppress pillar necks. Built two-leaf Tree tests cover round and square tips, both round-tip primary adjacent faces, secondary landing, and a separate wall. Square-tip Tree necks are tagged separately from their branch; a red wall-crossing test showed the earlier Tree-only selector skipped them. `crossingSupportStructureParts` now selects those tagged necks, classifies only bounded intended hits with `isIntentionalContactReach`, and maps a forbidden neck hit to Tree fallback. Untagged pillar necks remain outside this structural check. Full single-worker Vitest passed 130 files/1,278 tests in 222.10 s; build, type check, diff check, and reference probe passed, with the existing large-chunk and line-ending warnings. Do not mark the whole body-clearance gate passed from zero pillar crossings.

Next provenance-only substep: `buildSupportMesh` now tags an ordinary neck with its primary contact ID, point, normal and exact `sourceFace` only when the caller certified that face. The test compares `positions` and `indices` with an otherwise identical untagged build byte-for-byte. Adding this metadata revealed a classification trap: the Tree fallback had identified split Tree necks merely by the presence of contact intent, so a pillar neck on another wall would be called a Tree collision. `SupportComponent.structureKind: 'tree'` now marks only split Tree necks and the Tree selector uses it. A red pillar-neck regression reproduced the false fallback, then passed after explicit tagging. This is not a new exemption or a full pillar-neck collision policy. The generic collision index/preflight design is separate from these dental decisions.

The current `gapAlternateIds` field is a separate unfinished coverage mechanism. When present, both Step 2 preview and final generation independently recompute phase-zero contour samples from the current STL. A selected alternate must have the exact generated ID, source face, position, and normal inside the current contact strip; a forged or mismatched saved ID is rejected. The final build still applies secondary-landing and body-clearance checks. The named `dentalSecondaryLandingOnApprovedSide` predicate requires exact approved face/paint membership and a geometric source normal facing the downward-ray origin. This side check is fail-closed on reversed/inconsistent winding and does not prove the whole neck path clear. No code automatically chooses alternate IDs to repair the measured gaps yet. This staging preserves preview/build parity while the selection algorithm and island heatmap remain future work.

Do not describe the wrong-side check as a generic, fully modular API yet. `buildSupportMesh` accepts the reusable `landingAllowed(landing)` callback, but only `runSupportJob` for two-contour dental supplies `dentalSecondaryLandingOnApprovedSide`; other generators do not inherit it. That predicate covers the *endpoint* of a downward secondary ray, not the shaft, branch, brace, or wall traversal between endpoints. The latter is addressed only for selected dental component classes by `crossingAutomaticBodyContactIds` and `crossingSupportStructureParts` after building actual geometry. The shared lower-level `trianglesIntersect3D` predicate is generic and named. `createModelCollisionIndex` now extracts the reusable X/Z broadphase; `supportBodyConflicts` accepts an optional matching-model index, and dental `runSupportJob` shares one across all body checks. This is index reuse, not a generation-time path preflight or a generic-job safety policy. A future generic `bodyClearance` service still needs intentional tip exceptions, part/contact attribution, coordinate-frame validation, and result reporting; each domain supplies its own approved-face/side policy.

UI parity lesson: Step 2 owns `DentalPolicy.structure`, but the generic right panel previously displayed `settings.scatterAutoTree: false` beside a checked dental Tree switch. That was not a geometry bug—`dentalBuildSettings` applied the policy—but it falsely implied Tree was disabled. `SettingsPanel(dentalMode)` now suppresses the generic placement, Tree, Bracing, Roof/Cage, and preset controls during dental Steps 1–3 while retaining tip/pillar/foot/raft/lift controls. `DentalBar` is the only visible editor for dental Tree/Brace booleans. A static panel test and browser walk assertion protect this mapping; do not expose two settings sources for the same dental behavior again.

`dentalRimCoverage.ts` measures **final built automatic** contact IDs after all primary, secondary-landing, and pillar-body exclusions. The recomputed contour samples carry an `outer`/`opening` tag and their source 3D arclength. The job matches final component owners back to those exact source positions/normals, sums exact contour-edge lengths in source millimetres, sorts retained arclengths, and includes the closed-loop wraparound gap. A gap above twice the requested sampling spacing (currently 6 mm outer, 4 mm opening) sets a Step 3 review warning; a rim with zero retained contacts reports its full perimeter. This is a conservative **notification trigger**, not a dental or printability threshold. The warning is unavailable if contour identity cannot be verified. Neither the measurement nor the UI creates a contact or overrides a collision rejection. On the saved raw STL the opening maximum is 8 mm; browser import centres the source mesh and gives a 10.0 mm opening maximum in the live walk. Safe local resampling inside the same strip is still future work.

### Pose of the diagnostic GLB

The GLB review tool calls `rotationToDentalPose` after detection. This step transforms the displayed model and contours; it does not change triangle indices or face membership. Project all vertices onto the opening plane. Compute the principal axis of their 2 × 2 covariance matrix, then its perpendicular minor axis. Reject a nearly rotationally symmetric footprint when eigenvalue spread divided by trace is below `0.05`.

In principal-plane coordinates, normalize each point into the bounding rectangle. Keep points with major-axis fraction between `0.3` and `0.7`. On each minor-axis end, count occupied cells of a 40 × 40 grid in the outer 22% band. Reject when the larger count is below 20 or below twice the smaller count. The denser end determines the signed arch-front direction. Let `sourceSide = normalize(front × openingDirection)`. Map the source orthonormal frame `(sourceSide, front, openingDirection)` to the calibrated target frame defined by `targetOpening = normalize(0.03714905735, -0.68888926512, -0.72391403353)` and `targetFront = normalize(-0.01322175450, 0.72401182810, -0.68966082821)`, with `targetSide = normalize(targetFront × targetOpening)`. The rotation matrix is `targetFrame × transpose(sourceFrame)`. The implementation exports this rotation as a GLB node matrix. If arch-front estimation fails, the review tool writes no GLB; it does not guess a pose. These target directions come from the single approved reference pose, not from a universal print-angle rule.

The tests parse `docs/dental-reference/reference-aligner.stl`, assert both loop sizes and face counts, rotate the exact same triangles and require an identical face mask, require a cube to be inconclusive, and verify GLB output. Run [`run-review.bat`](run-review.bat) for a future STL. The read-only exploratory source is `scripts/probe-dental-edges.ts` with `DENTAL_PROBE_CONNECTORS=1` and `DENTAL_PROBE_OPENING=1`; the older colored reference model is [`support-area-review.glb`](../docs/dental-reference/support-area-review.glb). Its teal surface is the proposed area, not an approved clinical truth for other patients.

To recreate the current method in another language, preserve mesh indexing and triangle order. Calculate the orientation frame and a manifold edge-to-faces table. Extract two 60° outer chains and join them on the 20° edge graph. Rasterize and lift the central hole silhouette at both resolutions. Cut face adjacency along both closed loops and classify the two face groups. For each contour edge, use its two incident faces and the broad group IDs to seed one bounded 3D face-distance search on each side. Keep the `otherSide` faces whose search distance is 0.2 to 1.2 mm. Union the outer and inner masks. Sample each ordered contour at 3 mm or 2 mm spacing, respectively, and move each sample to a reachable exact source face within 1.5 mm in the selected mask. Preserve that face ID with the contact. At placement and final build, recompute the proposal and reject a changed mask, contour, or primary contact. Apply paint edits only within the recomputed mask. Reject an unapproved secondary model landing. If a required check fails, return an inconclusive result instead of a partially painted mask.

### Event-based topology-birth diagnostic (not yet a production island gate)

`src/core/analysis/topologyBirths.ts` accepts an indexed mesh in millimetres with Y increasing away from the plate. It rejects empty/malformed indices, non-finite coordinates, invalid height tolerance, duplicate source triangles, and edges used by more than two triangles; an open boundary itself is allowed. A two-pass triangle-edge traversal creates a typed-array CSR vertex adjacency. Sort referenced vertices by height, bucket heights within 0.00001 mm by default, activate each bucket, and union its same-height edges. Each resulting plateau with no active lower neighbor is a birth of a new connected sublevel-surface region; only then join the bucket to all lower neighbors. The output is source-vertex/plateau provenance and birth height, **not** an unsupported-island verdict. With V vertices and E indexed edges, the intended cost is sorting plus near-linear union-find, O(V log V + E α(V)), without a factor for layer count. The saved raw reference parsed to 186,976 vertices / 373,956 triangles; three standalone runs with topology validation observed 56 births in 202–214 ms. A separate no-contact legacy `checkSupports` run took 145 ms and emitted one clustered island warning; its downward-normal, proximity, clustering, and 50-problem cap make its count intentionally non-equivalent. These runs exclude parsing, orientation, support-path checking, and export, and are not a browser-worker responsiveness guarantee. The current `checkSupports` island heuristic remains unchanged. Next classify whether each birth has a valid built path to plate/raft and distinguish tiny numerical births; only then report unresolved candidates to either generator. No candidate can widen the dental strip.

`src/core/supports/supportPath.ts` is the next isolated **graph reducer**, not the geometric verifier. Input births have unique IDs and Y heights; input links name a source birth, a lower birth or `plate`, endpoint heights, automatic/manual origin, and a caller-supplied `verified` flag. Malformed identities, nonfinite heights, or unknown endpoints return `inconclusive`. Only verified links whose top does not exceed the source birth, whose bottom does not exceed the top, and whose bottom reaches the target birth or Y=0 plate enter the graph. Reverse breadth-first reachability from plate-linked births finds all resolved IDs; a second all-automatic traversal distinguishes manual-dependent IDs from ones with an automatic path. Cycles without a plate anchor remain unresolved. This is O(B+L) time and space after the links are supplied. Seven behavioral tests cover anchoring, disconnection, height reach, cycles, malformed inputs, and manual provenance. **`verified` is not a proof**: no caller currently derives it from built component joins, intentional-contact classification, and body clearance, so this module is not used by Generate/export. The next adapter must perform those geometric checks and map each topology birth to a source face/contact; until then, no birth is a certified supported or unsupported island.

### Limits and next safety gate

These measurements prove rotation consistency on one STL, not correctness on different aligners. An unusual trim, missing posterior section, scan hole, reversed/inconsistent winding, attachment, or second projected opening can cause abstention or a plausible but wrong candidate. Thresholds are calibrated only to the reference. The current two-contour implementation samples along the validated mesh contours into narrow exact-face strips rather than filling the broad face cut; Add paint cannot authorize a face beyond those strips. Before release, test distinct similar STLs with labeled allowed/forbidden faces and inspect final support-body paths. User approval of this example does not satisfy those gates.
